For changes to `~/.local/share/chezmoi/` (the chezmoi source tree), use a feature branch + PR workflow. Do **not** commit and push directly to `main`, even though it's a personal/solo repo.

**Why:** James wants CodeRabbit's PR-time review layer on dotfile changes — Codex's commit-time cross-provider review is one layer, CR is the second. Direct-to-main skips CR entirely. Validated 2026-05-14: pushed `54d422b` (tmux ⌘P sub-chat PR fix) direct to chezmoi main on the user's "go for it" — user pushed back: "why didnt we PR it to get the CR review?" Pick C (adopt PR workflow going forward) — the commit stayed on main, but future changes branch.

**How to apply:**
- Editing anything under `~/.local/share/chezmoi/`? Create a feature branch (`fix/...`, `feat/...`) before staging.
- `git push -u origin <branch>` and `gh pr create` instead of `git push` to main.
- CR runs against the PR — wait for its comments before merging.
- Merge via `gh pr merge` (squash) once CR + any other reviewers clear.
- Pairs with [[codex-dispatch]] (commit-time) — CR is the PR-time complement.
- Doesn't apply to runtime user files outside chezmoi source (`~/.tmux.conf` itself is generated by chezmoi apply — edit the source, not the destination).

**Worktree is mandatory, not just a branch.** A global `commit-on-drifted-branch-guard.sh` PreToolUse hook (at `~/.claude/hooks/`) blocks `git commit` on the primary checkout of ANY repo when branch ≠ default (main/master/staging) — not chezmoi-exclusive. Re-validated 2026-05-19 on jm-home-lab `chore/drop-shadowed-jm-commands`: same hook, same recovery via worktree. Assume the hook applies to jm-home-lab, oneonme-platform, and any other tracked repo without `GIT_COMMIT_ON_DRIFTED_BRANCH_OK=1` preset. Switching off main with `git checkout -b` on the primary checkout fails at commit time. Use `git worktree add .claude/worktrees/<slug> -b <branch>` from the chezmoi source root instead; primary checkout stays on `main`. Validated 2026-05-17 on `/jm-plugin-audit` updates section: branched on primary checkout → hook fired with "primary checkout drifted off default branch" → had to revert to main, redo via worktree, re-Edit in the worktree (the staged diff didn't survive the checkout dance and `git diff --cached` returned the stat summary not the patch when piped to a file, so `git apply` failed; just re-running the Edit in the worktree path was faster than fighting the patch). Skip the redo by going worktree-first from the start.

**Exceptions:** trivial one-line corrections that don't benefit from CR review (typo in a comment, whitespace), but lean toward PR — the friction is low.

**Drift handling:** When `chezmoi re-add` captures pre-existing live drift alongside the intended edit, the default move is **bundle + branch + PR in the same session**, not "defer drift to a separate session." Drift in a long-lived chezmoi target is almost always coherent feature work that just hadn't been committed yet — letting it sit risks `chezmoi apply` reverting it later. Triage the diff first: if it's coherent (related features, sensible commit story), write one descriptive commit that calls out new-vs-bundled in the PR body and ship it. Only split into two PRs if the drift is genuinely orthogonal to the new edit. Validated 2026-05-15 on visor-hud row 1 fix: initial response punted "110 lines of unrelated drift" to a future session; user redirected ("should def be in chez"); inspection showed the drift was cohesive (sanitize_title helper, user-ts walker, row 2 fleet cap) and shipped cleanly as one PR.
